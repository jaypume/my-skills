# 提交改动

在保留用户改动与暂存边界的前提下，快速完成本地提交。

## 默认原则

- 明确的提交请求授权本地 commit；范围可从上下文和 diff 判断时直接执行，仅在无法安全确定范围或目标时询问。
- 同一目的的代码、配置和必要配套改动合为一个 commit；实质独立的改动才拆分。
- 用户明确指定的分支、范围、拆分方式和 message 优先；默认不 amend、rebase、push 或创建 PR。

## 工作分支

先确认有可提交内容，再决定分支；创建分支属于本地提交准备，无需另行确认。

- 默认在当前分支提交，`main`、`master` 同样适用；遵循用户指定与仓库明确的分支约束。
- 只有 `origin`、没有 `upstream`，且通常直接推送、不走上游 PR 的仓库，默认在 `main`
  （或仓库实际默认分支）开发和提交；不因任务不同自动新建分支。用户要求 push 时直接推送到
  对应 `origin` 分支；仅要求 commit 不隐含 push 授权。已有 PR 或分支保护约束时遵循其要求，
  不仅凭 remote 名称判断工作流。当前已在任务分支时保留当前工作，不自动切回或合并到 `main`。
- 采用上游 PR 工作流、当前在任务分支时，结合本次改动、已有提交和关联 PR 判断归属，不只看分支名称。
  同一特性及其配套修复、测试、文档继续使用当前分支；明显无关的新任务另建分支。
- 从任务分支另起独立任务时，先 `git fetch upstream main`，再从最新 `upstream/main` 建分支，
  避免带入当前任务的无关提交。未配置 `upstream/main` 时使用已确认的上游主干；
  基线不明或 fetch 失败时说明问题，不静默使用旧基线。
- 需要新建分支时按目的使用 `feat/`、`fix/`、`docs/` 或 `chore/`，名称使用简短英文与短横线；
  同名已存在时使用新名称，不覆盖或自动复用已有分支。
- 从当前 HEAD 建分支时保留工作区与 index；从上游主干另起任务时，仅迁移本次任务的改动，
  保留原分支、无关改动及用户暂存边界。工作区混杂时优先用独立 worktree 承接选定改动，
  不为切分支整仓 stash、重置主干或改写已有提交。
- 新任务依赖当前分支尚未合入的实现，或无法安全拆分改动时，说明依赖并确认处理方式，
  不强行套用独立分支流程；迁移后重新核对相对上游的 diff，并验证受基线变化影响的行为。
- detached HEAD 时先从当前提交建立任务分支。
- 有未完成的 merge、rebase、cherry-pick 或未解决冲突时，先处理该操作的上下文，不套用普通提交流程。

## 提交流程

1. **盘点范围**：一次获取仓库根、当前分支、`git status --short --branch`、必要的 diff 和近期提交格式。
   区分 staged、unstaged、untracked；未跟踪文件需单独读取，普通 `git diff` 不包含其内容。
   大改动先看 stat/name-status，再展开候选文件；复用本轮仍有效的检查结果。
2. **确定批次**：按用户请求选定改动，遵循上面的分支规则。没有符合范围的改动时直接报告，不创建空提交或分支。
   已有 staged 内容须确认归属；文件被部分暂存时保留用户选定的 hunks，除非明确要求纳入整文件。
3. **暂存与核对**：用显式路径 `git add -- <paths>` 暂存已审阅内容；部分暂存的文件不直接整文件 add。
   核对最终 staged 路径与范围，始终执行 `git diff --cached --check`。
   只有 staged 内容恰好等于刚审阅且未变化的内容时，才省略重复的完整 diff；否则查看 staged diff。
4. **提交与确认**：通过检查后执行 commit，成功后读取新 commit 的 hash/subject 与状态，报告分支、提交和剩余改动。
   命令按成功依赖顺序执行；失败后不继续提交或宣称完成。

普通 `git commit` 会包含整个 index。已有暂存内容超出本次范围时，不擅自取消暂存或混入提交；
无法保留原暂存边界并完成请求时，说明冲突并询问。发现并发修改时重新确认受影响内容。

## Submodule 边界

- 默认排除子仓库 dirty 状态、HEAD 变化和父仓库 gitlink 更新；“提交全部”不构成更新 gitlink 的授权。
- 用户明确要求更新/添加 submodule 或提交 gitlink 时，先确认目标 commit 可从对应远端取得，再纳入父仓库提交。
- 未授权的 gitlink 若已 staged，保留 index 并说明边界，不直接执行会包含它的 commit。

## 检查与失败处理

- 只有范围混杂、暂存归属不清、异常删除/重命名、生成文件或敏感内容等实际信号才扩大检查。
  凭据、数据库、日志、缓存和异常大文件重点检查候选内容与新增行，不泛化扫描整个仓库。
- 提交任务不默认重跑测试、构建或全仓 lint；执行仓库要求或与改动直接相关的必要检查，复用仍有效的结果。
- message 基于实际 staged 改动，遵循仓库格式与 commitlint；不为提交任务新增测试、文档或提交记录。
- hook 失败时报告错误；hook 若修改文件，重新审阅后再暂存。未经授权不跳过 hook，不盲目重试或顺手修复无关代码。
- 不使用 `reset --hard`、`checkout --`、`clean` 等丢弃改动的命令，不修改、还原或删除无关用户内容。
