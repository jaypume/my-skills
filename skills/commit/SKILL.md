# 安全提交

在不丢失或覆盖用户改动的前提下，以尽可能少的工具轮次完成范围清晰的 Git 提交。

## 默认策略

- 用户明确要求提交即表示授权完成提交；除非存在实质阻塞，不要停在计划、分析或请求确认阶段。
- 合并同一目的的代码、配置和必要配套修改；仅在改动实质独立时拆分，避免为了文件类型或目录不同而过度拆分。
- 合并可并行的只读检查到一次工具调用中，并根据风险补查；不要用多次调用重复读取同一份 diff。
- 对小而一致、无敏感或异常文件的改动走快路径；混合改动、已有 staged 内容、二进制或大文件、生成物和可疑凭据走审慎路径。

## 工作流程

1. **单轮盘点**：确认仓库根目录和适用指令，并在一次工具调用中获取 `git status --short --branch`、staged/unstaged diff 概览及最近提交格式。仅在判断范围或风险需要时读取完整 diff、未跟踪文件内容或更多历史。
2. **划分批次**：根据改动目的决定一个或多个提交。保留用户已有 staged 状态；若 staged 内容与目标范围冲突，不擅自取消暂存或混入其他内容。
3. **定向安全检查**：只扫描候选批次，检查密钥、token、密码、私钥、认证响应，以及意外的大文件、二进制、缓存、日志、生成物和运行时配置。命中关键词不等于泄密，结合文件类型和 diff 判断；确认可疑时停止处理该文件并说明。
4. **明确暂存**：用具体路径暂存当前批次。只有确认整个工作树属于同一批次时才可使用 `git add -A`；不要用交互式命令。
5. **一次复核**：暂存后并行执行 `git diff --cached --check` 和完整 staged diff 复核。完整 diff 已足以确认内容时，不再重复查看等价的 stat/summary；只有大批次、重命名或二进制变化需要补看统计或 summary。
6. **提交**：根据实际 diff 和仓库历史生成简洁信息；存在 commitlint 时遵循 `type(scope): subject`。除非用户或仓库指令要求，不为单纯提交任务新增测试或修改代码。
7. **闭环**：提交后一次性获取提交 hash/subject 和 `git status --short`，报告已提交范围及剩余改动。多个批次按上述步骤连续完成，无阻塞时不要逐批请求确认。

## 需要暂停的情况

- 提交范围存在会显著改变结果的歧义，且无法从用户请求、diff 或仓库惯例判断。
- 候选内容疑似包含真实凭据、隐私数据、异常大文件或不应纳管的生成物。
- staged 内容属于其他工作，继续会覆盖、混入或要求取消用户的暂存选择。
- 必需检查或提交失败，且修复需要修改代码、扩大范围或执行破坏性操作。

## 安全边界

- 不使用 `git reset --hard`、`git checkout --`、`git clean` 或其他可能丢失改动的命令。
- 不修改、还原或删除与提交任务无关的用户改动。
- 不 amend、rebase、push 或创建 PR，除非用户明确要求。
- 不因新增 `.gitignore` 规则而自动取消跟踪已经纳管的文件。
- 不为通过检查而顺手修改代码；若提交前检查失败，报告失败并保留当前改动。
- 用户明确指定提交范围、拆分方式或提交信息时，以用户要求为准。
