# App 界面设计与验收

按当前项目与本次改动选择适用规则；已有项目技术栈和用户明确要求优先。局部改动只验证相关页面、状态和平台。

- **以项目技术栈为准**：个人跨平台 App 优先沿用 Tauri 的共享 Web 前端与 Rust 业务逻辑。macOS、Windows、iOS、Android 的差异通过响应式组件、输入方式和系统能力适配处理；平台设计规范用于约束体验，不自动引入另一套原生 UI 实现。系统能力先核实 Tauri API、插件和目标平台支持，确需原生扩展时收敛到平台适配层。
- **先建立视觉依据**：新增页面或调整视觉方向前，读取现有界面、组件和设计文档；有参考截图时，明确借鉴其布局、密度、层级或交互中的哪些部分。缺少参考时先利用现有产品和官方平台资料，说明设计假设；新产品或整体重设计可给出 1–2 个有实质差异的方向，局部修改沿用现有设计语言。
- **维护项目设计系统**：复用项目已有的权威设计文档；需要跨页面统一且尚无文档时，在对应 App 仓库维护 `DESIGN.md`，记录参考依据、字体角色、语义颜色、间距、图标、组件状态、响应式布局和平台适配规则，并在项目 agent 指令中指明入口。规则落实为共享 tokens 和组件，随实现同步更新；局部任务只维护相关规则。
- **共享品牌与组件，适配布局和交互**：同一产品共享颜色语义、字体层级、图标体系、术语和组件行为。桌面根据窗口大小组织侧栏、多栏信息、工具栏、键盘与焦点；移动端调整为适合触控的导航和内容层级，处理安全区、软键盘、返回行为与字体放大。优先复用组件和状态模型，按能力集中适配平台差异。
- **按职责选用技能**：Tauri/Web 界面的视觉方向或重设计从 `frontend-design`、`impeccable` 中选与任务匹配的一项主导，复用项目设计系统；配色、排版或图表选型按需使用 `ui-ux-pro-max`，先核对搜索结果的产品类型与技术栈，避免把营销页结构套入工具界面。`macos-design-guidelines`、`ios-design-guidelines`、`android-design-guidelines`、`web-design-guidelines` 按目标平台选用，并以当前官方规范校核。`swiftui-expert-skill`、`swiftui-pro` 仅在实际编写或评审 SwiftUI 代码时按需选用。
- **根据渲染结果迭代**：界面改动形成可运行版本后，使用真实内容或代表性数据，批量检查默认与最小窗口、窄屏、明暗模式、长文本或多语言、字体放大，以及所涉空、加载、错误和选中状态；检查主要操作、键盘或触控可达性与减少动态效果设置。截图后实际查看对齐、留白、文本截断、视觉重量和跨页面一致性，按影响修复，再验证受影响场景。
- **桌面窗口**：涉及桌面窗口创建、布局或恢复时，先读 [窗口记忆与启动验收](references/desktop-window.md)。
- **分层验证 Tauri 界面**：优先用后台运行的 Playwright 验证共享 Web 界面；涉及 Apple 平台时按需补 WebKit 检查。浏览器验证与 Tauri 宿主验收分别记录：窗口、标题栏、焦点、IPC、文件和权限等系统交互须在对应宿主验证，移动端须补模拟器或真机检查。编译成功、浏览器截图或截图回归均不能单独作为目标平台体验通过的依据；无法执行的检查明确说明原因和待验证步骤。
