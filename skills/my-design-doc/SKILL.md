# 设计文档写作

让读者能回答：要解决什么、方案如何工作、为什么这样选、哪些尚待验证。保持技术契约和证据边界准确，结构随内容调整。

## 组织内容

- 先看现有文档与项目约定，识别读者的判断任务。已有事实不凭润色改写，缺失证据明确留待验证。
- 开篇给出问题和设计结论；正文连贯展开运行流程、选型理由及关键约束。实现定位、详细来源与历史可放附录，理解方案必需的内容就近解释。
- 评估已有实现时，先比较同一问题下的行为，再说明采用点、差异与代价。保留来源和版本边界；代码路径存在不等于用户流程已通过验证。
- 重构优先合并重复、缩短句子、解释概念；不设统一字数、章节数或图表数量。用户要对照试读时另存副本，正式定稿再按要求收敛。

## 选择表达形式

| 读者要理解什么 | 优先形式 |
| --- | --- |
| 一个结论及其原因 | 短段落 |
| 同类选项的差异 | 按共同维度对齐的表格；单元格保持简短 |
| 流程、归属、状态或消息顺序 | 对应的 Mermaid 图；一图解决一个主要问题 |
| 有共同口径的真实测量 | 注明来源、单位、条件的数据表或图 |
| 请求、响应、配置 | 格式化代码块，嵌套内容展开 |

流程已被前图解释清楚时，不再为同一结论补图。参数含义不同，即使单位相同也不能画成性能排名。默认采用 Markdown；需要精确布局且 Mermaid 不易表达时再考虑 SVG。

需要选型表、正文与附录划分、JSON 展开示例时，读取 [表达示例](references/examples.md)，按内容取用，不整套复制。

## 工具按需使用

- `writing-clearly-and-concisely`：句子和段落仍冗长时用于润色。
- `mermaid-diagrams`：需要选择图型或编写 Mermaid 时使用。
- `pretty-mermaid`：需要静态预览或样式辅助时使用，不要求每篇文档都调用。

这些是可选辅助；未安装时仍可完成文字与表格工作。图示遵循项目的布局、配色和渲染规则，源码只保留一份。

## 交付前检查

- 从头阅读正文，是否能理解方案及取舍，而不必反复查附录？重复文字或图表能否合并？
- 对照原文确认契约、数字、单位和未知项未被误改。JSON 格式化后应能解析且含义相同。
- 检查标题层级、相对链接、代码围栏。新增或修改 Mermaid 时，用官方 Mermaid CLI 渲染，并按实际展示尺寸检查文字、连线和阅读顺序；只解析成功不代表视觉通过。
- 交付说明使用实际形式名称，如“Markdown 对比表”“Mermaid 流程图”；给出文件位置，并如实说明尚未完成的验证。
