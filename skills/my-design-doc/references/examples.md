# 表达示例

以下仅示范组织方式，技术内容是假设场景；不作为固定章节模板。

## 选型：让每一列回答同一个问题

当候选较少、比较维度固定时，可以横向对齐；候选较多时改为每行一个候选，避免表格过宽。

| 判断维度 | 同步等待 | 后台执行与完成通知 |
| --- | --- | --- |
| 等待期间可做什么 | 当前调用等待结果 | 可处理独立工作 |
| 如何得知完成 | 原调用返回结果 | 后续通知送达结果 |
| 实现代价 | 调用生命周期简单 | 需要结果归属、去重和暂停控制 |

选择理由紧接表格：若用户需要同时推进独立工作并自动处理结果，采用后台执行与完成通知；若命令很短且调用方必须立即使用结果，同步路径仍适用。

## 正文与附录：按阅读依赖划分

正文应解释运行方式、采用理由、关键边界与验证缺口。例如：“用户停止自动运行后，后台结果可以保存，但只有用户恢复后才继续。”这会影响读者对行为的判断，应放在流程或停止规则旁。

支撑这一判断的完整源码定位表、历史提交清单和长日志可以放附录，并从相关正文链接过去。篇幅长本身不是放入附录的理由。

## JSON：展开结构，保留契约

调用示例：

```json
{
  "command": "python train.py",
  "yield_ms": 1000,
  "timeout": 7200000
}
```

响应结构示意，仅展示状态与输出字段：

```json
{
  "state": "running",
  "output": [
    {
      "stream": "stdout",
      "text": "training started\n"
    }
  ]
}
```

如果原文定义的是完整响应，格式化时保留全部字段；只有明确展示局部结构时才删减并标注。不要为了可读性将毫秒改成秒、把数字改成字符串，或在标准 JSON 中加入注释。
